## The Data Density Problem

With 50-200 contributors, arbitrary queries often return "insufficient data." The product at this stage should be **curated reports** (we decide what's interesting and compute it), not **open queries** (buyer asks anything).

Think weekly market research report, not SQL database.

### What Works at Low Density

| Approach | Min Contributors | Why |
|----------|-----------------|-----|
| **Network-wide aggregates** | 20+ | "40% of all prompts are debugging" — one big cohort |
| **Weekly snapshot reports** | 50+ | Pre-computed, curated, covers the interesting dimensions |
| **Single-dimension breakdowns** | 100+ | "Debugging by language" — enough per bucket to be meaningful |
| **Cross-dimension queries** | 500+ | "TypeScript + debugging + senior" — needs density in every slice |
| **Real-time MCP queries** | 1000+ | Arbitrary exploration with k-anonymity guarantees |

Phase 3 targets the first three rows. MCP query layer comes when we hit 500+.

## What We're Building

### 1. Pre-Computed Reports (daily/weekly cron)

The platform computes aggregate reports on a schedule. These are the product.

**Weekly Snapshot Report:**
```json
{
  "report": "weekly_snapshot",
  "period": "2026-02-10 to 2026-02-16",
  "network": {
    "active_contributors": "50-100",
    "total_contributions": 3400,
    "avg_per_contributor": "30-50"
  },
  "intents": {
    "debugging": { "share": 0.38, "trend": "+3% vs last week" },
    "feature_build": { "share": 0.27, "trend": "-1%" },
    "learning": { "share": 0.14, "trend": "+5%" }
  },
  "languages": {
    "typescript": 0.44,
    "python": 0.23,
    "rust": 0.08
  },
  "patterns": {
    "most_common_flow": "exploration → feature_build → debugging",
    "avg_session_depth": "6-10 prompts",
    "peak_usage": "afternoon (35%)"
  },
  "insight": "Learning-related prompts are growing fastest, up 5% week-over-week. Developers are increasingly using Claude Code for understanding code, not just writing it."
}
```

**Daily Pulse (lighter, just the numbers):**
```json
{
  "report": "daily_pulse",
  "date": "2026-02-19",
  "contributions": 520,
  "top_intent": "debugging (41%)",
  "top_language": "typescript (46%)",
  "notable": "Error-paste prompts spiked 15% today"
}
```

The `insight` field is generated by running the structured data through an LLM — turns numbers into a readable narrative.

### 2. REST API Endpoints

```
# Free — network health
GET /v1/reports/pulse
  Returns: Latest daily pulse
  Auth: None
  Purpose: Teaser, shows what's available

# Paid — weekly snapshot
GET /v1/reports/weekly
  Returns: Current week's snapshot report
  Payment: x402 ($0.05)

GET /v1/reports/weekly/:date
  Returns: Historical weekly report
  Payment: x402 ($0.05)

# Paid — single-dimension breakdown
GET /v1/reports/breakdown/:dimension
  Dimensions: intent, language, framework, complexity, domain, session_type
  Params: period (7d, 30d)
  Returns: Distribution with trends
  Payment: x402 ($0.03)
  Privacy: Only dimensions with 50+ contributors shown

# Paid — comparison (when density allows)
GET /v1/reports/compare
  Params: dimension, segments[] (max 3), metric
  Returns: Side-by-side segment comparison
  Payment: x402 ($0.08)
  Privacy: Each segment must have 50+ contributors or returns "insufficient data"

# Free — what's available
GET /v1/reports/catalog
  Returns: List of available reports + dimensions + data freshness
  Auth: None
```

### 3. x402 Payment Integration

```
Buyer makes request to paid endpoint
  │
  ├─ API returns 402 Payment Required
  │   Headers:
  │     X-Payment-Required: true
  │     X-Payment-Amount: 0.05
  │     X-Payment-Currency: USDC
  │     X-Payment-Network: base
  │     X-Payment-Address: 0x... (Pollen treasury)
  │
  ├─ Buyer's x402 client signs payment
  │
  ├─ Buyer retries with payment proof header
  │
  └─ API verifies payment → returns report
```

Any x402-compatible client works — doesn't have to be MCP. Could be curl with a wallet plugin, a script, or eventually the Pollen MCP server.

### 4. Report Computation Pipeline

```
Daily cron (CF Worker scheduled trigger):
  │
  ├─ Aggregate today's contributions by intent, language, etc.
  │
  ├─ Apply noise (±2-5% on all percentages)
  │
  ├─ Compare to previous period (compute trends)
  │
  ├─ Generate narrative insight (LLM call on the numbers, not on prompts)
  │
  ├─ Store report in KV (fast reads)
  │
  └─ Store in D1 (historical archive)

Weekly cron (Sunday midnight):
  │
  ├─ Aggregate the week's data
  │
  ├─ Compute cross-dimensional insights
  │
  ├─ Generate longer narrative with key takeaways
  │
  └─ Store weekly report
```

### 5. Revenue Tracking

```sql
CREATE TABLE query_revenue (
  id              TEXT PRIMARY KEY,
  buyer_address   TEXT,
  endpoint        TEXT,
  payment_amount  REAL,
  payment_tx      TEXT,
  timestamp       INTEGER
);
```

All x402 payments tracked for contributor payout calculation in Phase 4.

- [ ] Revenue is tracked per query
